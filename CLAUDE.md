## Що це за проект

Self-hosted веб-аплікейшен для командних ретроспектив. Один бінарний файл — ПМ запускає локально, робить проброс порта, розсилає invite links команді. Після ретро тушить сервер. Безкоштовна альтернатива платним SaaS типу Retrium або EasyRetro.

До 20 учасників на ретро. Цільова аудиторія — невеликі продуктові команди.

## Стек — жорсткі обмеження

| Що | Чим | Примітка |
|---|---|---|
| Мова | Go | Тільки Go, без CGO |
| База даних | SQLite | Файл `retro.db` створюється в папці бінарника через `os.Executable()` |
| Фронтенд | HTML + CSS + Vanilla JS | Тільки Go шаблони, **без React, Vue, Node** |
| Real-time | WebSocket (gorilla/websocket) | Або SSE якщо WebSocket надлишковий |
| Збірка | Один бінарний файл | `postup` / `postup.exe` |

**Заборонено:** Docker, Node.js, npm, будь-які зовнішні рантайми. Користувач просто запускає бінарник.

**Дистрибуція:** GitHub Releases, zip-архіви для всіх платформ:

```
postup-windows-amd64.zip
└── postup/
    └── postup.exe

postup-macos-amd64.zip
└── postup/
    └── postup

postup-macos-arm64.zip
└── postup/
    └── postup

postup-linux-amd64.zip
└── postup/
    └── postup
```

Користувач розпаковує архів і запускає бінарник. `retro.db` створюється автоматично в тій самій папці `postup/` поряд з бінарником — через `os.Executable()`. Обидва файли завжди разом, випадково видалити БД окремо складніше.

## Конвенції

### Handlers
- Один файл на розділ: `handlers/users.go`, `handlers/retros.go`
- Назва функції: `HandleUsersIndex`, `HandleUsersCreate`, `HandleUsersDelete`
- Патерн: перевірка авторизації → читання параметрів → бізнес-логіка → відповідь
- Помилки: `http.Error(w, "...", http.StatusXXX)` для API, редирект для форм

### Моделі
- Структури в `internal/models/`, назви в однині: `User`, `Team`, `Retro`, `Card`
- ID завжди `int64`
- Дати: `time.Time`, зберігаються в SQLite як `TEXT` в форматі RFC3339

### Шаблони
- Базовий layout: `templates/layout.html`, блок `{{block "content" .}}`
- Дані передаються як `map[string]interface{}` або типізована структура
- i18n: функція `t(key)` доступна в шаблонах через `template.FuncMap`

### Міграції
- Нумеровані файли: `001_init.sql`, `002_add_teams.sql`
- Накочуються автоматично при старті якщо нові є
- Відкат не передбачений — тільки вперед

### CSS
- CSS змінні для теми: `--bg-primary`, `--text-primary`, `--accent-purple: #6c6fff`, `--accent-green: #2dd4a0`
- Темна тема за замовчуванням, `[data-theme="light"]` для світлої
- Без зовнішніх CSS фреймворків

### Сесії
- Cookie `session_id`, TTL 12 годин
- Зберігаються в SQLite таблиці `sessions`
- Middleware `RequireAuth` і `RequireAdmin` в `internal/middleware/`

## Бізнес-логіка — критичні правила

Ці правила агент повинен знати щоб не зламати логіку:

- **Картка:** редагувати і видаляти може тільки автор. Переносити між колонками — тільки автор. Голосувати — будь-який учасник.
- **Голоси:** ліміт задається при створенні ретро (дефолт 10). Учасник розподіляє як хоче.
- **Action items:** обовʼязкові поля — відповідальний (зі списку присутніх) і дедлайн. Автоматично переносяться в першу колонку наступного ретро тієї ж команди.
- **Шаблон після ретро:** редагування створює копію як новий шаблон, оригінал не змінюється.
- **Invite link:** містить зовнішній IP з `api.ipify.org`. Формат: `http://{ip}:{port}/invite/{token}`
- **Перша колонка** завжди фіксована (action items з попереднього ретро), **остання** завжди фіксована (нові action items). Середніх від 1 до 5.

  Перед комітом перевірити `git status` — переконатись що `*.db`, бінарники, `.DS_Store` не потрапляють.

**Стратегія git під час UAT:**
- Локальні коміти після кожного фіксу — тільки на машині оператора
- `git push` НЕ робимо під час UAT
- Після завершення UAT — один `git push` як перша публічна версія v1.0
- GitHub побачить фінальний стан, вся "кухня" фіксів залишається локально

**Правила роботи в цьому режимі:**

1. **Одна проблема — один фікс.**
   Не чіпай нічого крім того що описано в поточному зауваженні.
   Не рефактори, не покращуй сусідній код "поки вже тут".

2. **Перед фіксом — діагноз.**
   Спочатку знайди причину і скажи де саме проблема.
   Тільки після підтвердження — правиш.

3. **Після кожного фіксу — перевірка регресії.**
   Запускай тести:
   ```
   go test ./... -v 2>&1 | tee /tmp/test_out.txt | grep -c "^=== RUN" && grep -E "^(ok|FAIL)" /tmp/test_out.txt
   ```
   Якщо щось зламалось — кажи одразу, не приховуй.

4. **Мінімальний diff.**
   Зміна повинна бути найменшою можливою для вирішення проблеми.
   Якщо фікс торкається більше ніж 2–3 файлів — попередь і поясни чому.

5. **Локальний коміт після кожного фіксу.**
   Повідомлення коміту: `fix: {короткий опис проблеми}`
   Без push — тільки локально.
